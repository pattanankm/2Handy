3. Concurrency Control & Race Condition Prevention Audit

To satisfy Section 2.1 of the CP3 Specification, the 2Handy architecture implements and proves both concurrency control paradigms:

A. Optimistic Concurrency Control (OCC) in MongoDB

  • Mechanism: Every product document in MongoDB maintains an atomic integer version field. Product updates and purchases execute via atomic find_one_and_update requiring version == expected_version and incrementing version via $inc: {"version": 1}.
  • HTTP Status Mapping: When a concurrent write collides, the server returns HTTP 409 Conflict (or HTTP 412 Precondition Failed when using stale If-Match headers).
  • Dual-Database Integrity: When buying an item in POST /api/v1/orders, if MongoDB OCC rejects the sale because another user purchased the last item, PostgreSQL automatically rolls back the order transaction. Zero orphan rows remain.

B. Pessimistic Concurrency Control (PCC) in PostgreSQL

  • Mechanism: Order state transitions (e.g. POST /api/v1/orders/{id}/complete) and critical user updates acquire an explicit row lock inside a database transaction boundary using SELECT ... FOR UPDATE.
  • Blocking & Serialization: Concurrent requests are blocked until the lock-holding transaction commits. Subsequent requests inspect the updated status, detect the order is no longer pending, and safely abort with HTTP 409 Conflict.
